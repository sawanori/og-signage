### [重大度: critical] RTC未搭載によるオフライン再起動時の時刻喪失と全表示・イベント状態・スケジュールの破綻
- 該当箇所: 要件定義書 23節、3.5節 / implementation-plan.md 6節（Assumption 16）、10節 / task_005, task_021 / acceptance-checks check_013, check_016
- 壊れ方: 停電やネットワーク障害時に Pi の電源が抜き差し（オフライン再起動）されると、Raspberry Pi 4 には RTC（ハードウェア時計）がないため、NTP 同期ができずシステム時刻が `fake-hwclock` の前回保存日時または大幅にズレた過去時刻（場合によっては 1970年や前日以前）で起動する。これにより `lib/event-status.ts` の `TODAY` / `STARTING SOON` / `NOW HAPPENING` 判定が全滅し、「本日のイベント」が一切表示されなくなる。さらに表示スケジュール（深夜の黒画面判定）が狂って昼間に画面が真っ暗になる、あるいはネットワーク復旧時に TLS 証明書の有効期限外判定で HTTPS 通信（Cloudflare Workers への config 取得）がエラーとなり永久にオンライン復帰できなくなる。
- 根拠: Raspberry Pi 4 単体にはバッテリーバックアップ付き RTC が非搭載であること、および Linux の NTP デーモン（systemd-timesyncd 等）はオフライン環境下で時刻を復元できないことは技術的事実（確信度: 高）。計画書では `Asia/Tokyo` の判定ロジック（task_005）しか考慮しておらず、OS レベルの時刻保持手段が一切言及されていない。
- 修正案: 
  1. ハードウェアとして I2C 接続の RTC モジュール（DS3231 等、数百円）の搭載を必須要件に加える。
  2. Agent 起動時、オフラインかつ RTC もない場合のフェイルセーフとして、ローカルに保存されている `events.json` や `config.json` のタイムスタンプより過去には時刻を巻き戻さないガード処理を入れ、時刻未同期フラグがある場合は「時刻未確定」の旨を画面隅に小さく出し、スケジュールによる消灯処理をバイパスする。

### [重大度: critical] SDカードへの過剰書き込みと電源断によるファイル破損・ハードウェア突然死
- 該当箇所: 要件定義書 17節、20節、41節 / implementation-plan.md 10節 / task_020, task_022 / acceptance-checks check_009, check_013
- 壊れ方: 30秒ごとの config ポーリング、60秒ごとの Heartbeat、ログ書き込み、Chromium のキャッシュ・Local Storage・プロファイル書き込み、さらに systemd-journald のログが SD カードに常時フラッシュされ続ける。受付スタッフや清掃員が電源プラグを直接抜く（完成条件9, 13で想定）運用を繰り返すと、ファイルシステム（ext4）のジャーナル破損、あるいは書き込み中の `events.json` / `config.json` の 0 バイト化（破損）が発生し、次回起動時に Agent が JSONDecodeError でクラッシュループする。また数ヶ月〜1年程度で SD カードの書き込み寿命（TBW）を迎え、メディアが Read-Only 化してサイネージが永久停止する。
- 根拠: Raspberry Pi OS のデフォルト構成では Chromium が `/home/*/.cache` や `/home/*/.config` へ膨大な一時ファイルを書き込み続けること、安価な SD カードが電源断耐性を持たずブロック破損しやすいことは組み込み運用の基本事実（確信度: 高）。計画書の task_020 では「原子的 rename」しか触れておらず、OS 全体の write 耐久設計（overlayfs や tmpfs）が皆無。
- 修正案:
  1. `/var/log` や Chromium のプロファイルディレクトリ（`--user-data-dir`）、一時ファイル置換領域を `tmpfs`（RAM ディスク）上に配置する。
  2. 保存領域（`/var/lib/sharehouse-signage`）への書き込み時は `fsync` を徹底し、破損検知時の `.bak` からのフォールバック復元処理を実装する。
  3. 可能であれば Raspberry Pi OS の `overlayfs`（Read-Only ルート）を有効化し、データ領域のみ別パーティションとしてマウントするか、SD カードではなく高耐久産業用 microSD または USB 接続 SSD/eMMC を採用する。

### [重大度: critical] 表示バンドル未配置時・破損時の起動デッドロックと永久白画面
- 該当箇所: 要件定義書 19節、23節 / implementation-plan.md 7節、11節 / task_014, task_021, task_022

  3. バンドル更新完了時、Agent からローカル WebSocket または Chromium のリモートデバッグポート（DevTools Protocol）経由で `Page.reload` を発行し、確実に画面を再読み込みさせる。

### [重大度: high] Wayland (labwc) 環境下での Chromium と mpv の全画面切替・前面表示・フォーカス復帰の破綻
- 該当箇所: 要件定義書 18節、19節 / implementation-plan.md 6節（Assumption 13） / task_003, task_021 / acceptance-checks check_008
- 壊れ方: Raspberry Pi OS Bookworm 64bit は Wayland（labwc）が標準である。キオスクモードで最大化・最前面に張り付いている Chromium の裏側で Python から `mpv --fs` を別プロセス起動した場合、Wayland のセキュリティモデルとコンポジタの仕様により、新しく起動した mpv ウィンドウが背面に隠れる、または全画面化できずに画面中央に小さくポップアップする。さらに動画終了後に mpv プロセスが死んだ際、Chromium にウィンドウフォーカスが戻らず、黒画面、デスクトップ背景、またはマウスカーソルが露出したまま固まる。

  1. `labwc` の設定（`rc.xml`）に `windowRule` を記述し、`app-id="mpv"` を常に最前面（`alwaysOnTop`）、デコレーションなし、フルスクリーン固定に設定する。
  2. または、Chromium と mpv のプロセス切替という不安定な二重管理をやめ、Chromium 内部で HTML5 `<video>` タグを用いて再生するか、動画再生中は Chromium のウィンドウを最小化/非表示にする明示的な IPC 連携を設計する。

### [重大度: high] 登録後30秒反映の物理的破綻（ポーリング間隔・ダウンロード・UI検知の遅延累積）
- 該当箇所: 要件定義書 21節、45節（完成条件3） / implementation-plan.md 2節 / task_014, task_020 / acceptance-checks check_003
- 壊れ方: 管理画面で受付スタッフがイベントを登録した瞬間、直前に Pi の 30秒ポーリングが走っていた場合、次回の `GET /api/device/[token]/config` までに最大 30秒かかる。そこから新着画像のダウンロード（数秒〜回線次第で数十秒）、Agent によるローカル JSON 保存、さらに表示ページ（フロントエンド）が `http://localhost:8080/local/state` を 1秒周期でポーリングして変更を検知するまでの累積遅延により、総反映時間は「30秒 + α」となり、完成条件3「登録後30秒以内にサイネージへ反映される」および acceptance-checks check_003（最大値30秒以内）を 100% 達成できずテストが失敗する。
- 根拠: ポーリング間隔が 30秒であるシステムにおいて、事象発生からクライアント検知までの最悪レイテンシは通信時間を除いても 30秒ジャストであり、通信・ファイル I/O・DOM 更新を加えた最大値は数学的に必ず 30秒を超える（確信度: 高）。

  1. 完成条件の SLA を「同期検知後 10秒以内、登録から最大 40〜45秒以内」に現実的な値へ緩和する。
  2. または要件を満たすため、Pi のポーリング間隔を 10〜15秒に短縮する（If-None-Match 304 を返すため Workers 負荷は軽微）。あるいは MVP では見送った Server-Sent Events (SSE) または WebSocket による即時通知を導入する。

### [重大度: high] Workers 経由の動画中継ストリーミングによるリソース枯渇と通信エラー
- 該当箇所: implementation-plan.md 6節（Assumption 6）、9節 / task_008, task_012 / acceptance-checks check_023
- 壊れ方: Pi が動画をダウンロードする際、Workers の `GET /api/device/{token}/media/{mediaId}` を介して Range ヘッダー付きで R2 から中継（プロキシ）する設計になっている。1ファイル最大 2GB（Assumption 7）の動画を Pi が chunk で並行または連続取得する際、Cloudflare Workers のサブスクリプション/プラン（Workers Free では CPU 時間 10ms、Paid でもストリーミング中の CPU 制限やタイムアウト制約）に抵触し、接続切断や 502/504 Bad Gateway が多発する。さらに Workers のリクエスト数・帯域の不要な消費を招く。
- 根拠: Workers を大容量メディアのプロキシとして常時中継させるのは Cloudflare のアンチパターンであり、Workers のメモリ上限（128MB）や CPU 時間制限によるパイプライン詰まりのリスクが高い（確信度: 高）。「R2 のアクセスキーをアプリに持たせない」という理由だけで Worker 中継を選択しているが、R2 は Workers 内部で署名付き URL（Presigned URL）を生成して 302 リダイレクトさせることが可能。
- 修正案:
  - 端末用メディア取得 API は、Worker でトークン認証を行った後、有効期限付きの R2 Presigned URL を発行して `302 Found` でリダイレクトさせる。Pi は R2 から直接 Range GET で大容量動画をダウンロードする構成に変更する。

### [重大度: high] Worker 経由のマルチパートアップロードによる Worker メモリ溢れと二重ホップ
- 該当箇所: implementation-plan.md 6節（Assumption 7）、9節 / task_008 / acceptance-checks check_005
- 壊れ方: ブラウザから 10MB のパートを Worker へ送信し、Worker が R2 バインディングの `uploadPart` を呼ぶ設計（`PUT /api/media/uploads/[uploadId]/parts/[n]`）。Next.js Route Handlers (vinext) がリクエストボディを処理する際、ストリームをメモリ上にバッファリングすると Workers の 128MB メモリ制限を圧迫する。また、ブラウザ→Cloudflare Edge→R2 の二重アップロード通信となるため、回線速度が遅い環境や複数パート同時送信時に Worker 側で CPU/Wall-clock タイムアウトが発生し、アップロードが失敗・ハングする。
- 根拠: Next.js on Workers (vinext) のリクエストハンドラで大容量バイナリの `request.arrayBuffer()` を行うと容易にメモリ制限や実行時間制限に達する（確信度: 高）。

### [重大度: high] Chromium 長期連続稼働によるメモリリークと OOM Killer によるクラッシュ放置
- 該当箇所: 要件定義書 42節 / TECH_STACK.md 10節 / task_022
- 壊れ方: `chromium-kiosk.service` を `Restart=always` で常駐させる計画だが、定期的なブラウザプロセスの再起動やメモリ監視の仕組みが存在しない。SPA（React）をキオスクモードで 24時間365日動かし続けると、タイマーイベント、DOM 差し替え、Chromium 内部の GPU バッファ保持によりメモリ使用量が漸増する。4GB RAM を搭載していても、数週間〜1ヶ月で Chromium の Renderer プロセスが OOM Killer（Out of Memory）によって SIGKILL され、「悲しい顔（Aw, Snap!）」画面が表示されたままハングアップする。
- 根拠: 長期運用のデジタルサイネージにおいて、Chromium のメモリリークは極めて一般的な障害原因であり、定期的なプロセス再起動（リフレッシュ）なしに数ヶ月以上の無停止稼働を維持することは困難（確信度: 高）。systemd は「メインの Chromium プロセスが落ちない限り Renderer のみのクラッシュを検知できない」。

### [重大度: high] 2GB動画アップロード許可と1GB空き容量下限の矛盾によるダウンロード/削除の無限ループ
- 該当箇所: implementation-plan.md 6節（Assumption 7） / task_020 / acceptance-checks check_033
- 壊れ方: 最大 2GB の動画アップロードを許可している一方で、Pi Agent のディスク管理は「空き容量の下限（1GB）を下回ったら不要ファイルを削除」となっている。SD カードまたはディスクの空き容量が 2.5GB の状態で 1.8GB の新規動画が登録されると、ダウンロード中に空き容量が 1GB を下回る。ダウンローダーは容量不足エラーを起こし、ファイルを削除するが、プレイリスト内のファイルのため次回同期で再度ダウンロードを試みる。この「ダウンロード試行 → 1GB 違反で中断・ロールバック → 再試行」の無限ループに突入し、ネットワーク帯域を食い潰して CPU が高負荷になり、SD カードに猛烈な書き込み負荷がかかり続ける。
- 根拠: 許容する最大ファイルサイズ（2GB）が、ローカル空き容量の安全マージン（1GB）を上回っており、ディスク枯渇防止アルゴリズムとして破綻している（確信度: 高）。
- 修正案:
  - Pi の最低要求空き容量閾値を「（登録されている最大動画サイズ × 1.5）または最低 5GB」に設定する。空き容量が不足している場合は、中途半端なダウンロードを開始せず即座に `DOWNLOAD_FAILED`（容量不足）ログをサーバーに送信し、管理画面に警告を出す。また、動画アップロード時のファイルサイズ上限もサイネージ用途として現実的な 300MB〜500MB 程度に引き下げる。

### [重大度: high] 縦型ディスプレイ（90度回転）と mpv 全画面描画の回転ミスマッチ
- 該当箇所: 要件定義書 8.0節、15節 / TECH_STACK.md 14節 / task_003, task_021 / acceptance-checks check_014
- 壊れ方: 縦型サイネージ（1080x1920）では、OS/ディスプレイ設定（KMS/Wayland）で画面を 90度または 270度回転させて出力する。しかし、Chromium は CSS/解像度に従って縦長（1080x1920）に描画されるのに対し、外部プロセスの mpv を単に `--fs` で起動すると、mpv が物理ディスプレイの生のスキャン方向（横向き 1920x1080）に描画してしまい、動画が 90 度横倒しで再生される、あるいは上下左右が激しくクロップされてアスペクト比が崩壊する。
- 根拠: Linux/Wayland 環境において、フルスクリーン起動された mpv がコンポジタ側の画面回転トランスフォームを自動で正しく継承しないケースは多発する（確信度: 高）。task_003 のスパイク項目に「4Kディスプレイへの1080p出力」はあるが、「画面回転時の mpv 描画検証」が完全に抜けている。
- 修正案:
  - 端末設定（`device.orientation`）が `portrait` の場合、Agent が mpv を起動する際の引数に `--video-rotate=90`（または 270）を動的に付与するロジックを `player.py` に組み込む。task_003 の検証項目に「縦型回転時の mpv 全画面再生確認」を必須として追加する。

### [重大度: medium] Pi Agent 本体の遠隔更新・デプロイ機構の完全欠落
- 該当箇所: 要件定義書 23節 / implementation-plan.md 7節 / task_014, task_020, task_022
- 壊れ方: 表示用 Web バンドル（`displayBundle`）の R2 経由の自動更新は考慮されているが、Python Agent 自体（`raspberry-pi/agent/*.py`）のバグ修正やアップデート手順が計画から完全に欠落している。本番稼働後に Agent のバグ（Heartbeat 送信漏れ、mpv 制御のデッドロック、同期ロジックの欠陥など）が発覚した場合、現場に出向いてキーボードを接続し手動で `git pull` やスクリプト更新を行わない限り、一切の不具合修正が不可能になる。
- 根拠: Phase 2（将来）に「遠隔再起動」はあるが、Phase 1 では Agent 本体の自動アップデートやスクリプト更新のタスクが task_001〜023 のどこにも存在しない（確信度: 高）。

### [重大度: medium] ブラウザ側でのギガバイト級動画デコード・SHA-256 計算による管理画面クラッシュ
- 該当箇所: implementation-plan.md 6節（Assumption 8） / task_008 / acceptance-checks check_005
- 壊れ方: 動画アップロード時、「ブラウザ側で `<video>` と `<canvas>` を用いてサムネイル生成と動画の尺を取得し、Web Crypto API で SHA-256 を計算する」としている。受付スタッフが使用する一般的な PC やノート PC で、数百 MB〜2GB の大容量 H.264 ファイルをブラウザに読み込ませて全バイトのハッシュ計算やデコードを走らせると、メインスレッドまたはメモリが飽和し、ブラウザタブがクラッシュ（Out of Memory）するか画面が長時間フリーズする。スタッフ向け「直感的な操作性」の要件を満たせない。
- 根拠: ブラウザ環境におけるギガバイト単位の File オブジェクトの SHA-256 全量計算および `<video>` シークによるサムネイル抽出は、クライアント端末の CPU・メモリを過大に消費する（確信度: 高）。
- 修正案:
  - SHA-256 計算はファイル全量ではなく Chunk 読み出しの Web Worker（バックグラウンドスレッド）で行い進捗バーを表示する。または、クライアントでの重い SHA-256 計算は廃止し、R2 側が返す ETag（マルチパートアップロード時は各パートハッシュの連結）を照合キーとして活用する。

### [重大度: medium] Turso HTTP クライアント環境下でのトランザクション競合と `content_version` 競合
- 該当箇所: implementation-plan.md 7節、9節、10節 / task_004, task_007, task_009 / acceptance-checks check_025
- 壊れ方: 「内容を変更する操作はすべて、同じトランザクションで `content_version` を 1 増やす」としている。しかし Cloudflare Workers 上で動作する `@libsql/client/web`（HTTP トンネル経由）は、ステートフルな長い対話型トランザクション（Interactive Transaction）をサポートしていないか、極めてレイテンシに敏感である。複数スタッフによる同時更新や、Cron Trigger（task_013 のログ削除や天気取得）が並行して走った場合、Turso へのトランザクションがロック競合でロールバック（500 エラー）し、画面操作が頻繁に失敗する。
- 根拠: libSQL の HTTP API (`/v2/pipeline`) 上で動作する Drizzle ORM のトランザクションは、WebSocket 接続とは異なりパイプライン化されたバッチ実行に限られ、競合時のリトライ機構がないと排他制御エラーが発生しやすい（確信度: 高）。
- 修正案:
  - `content_version` を別テーブル（`app_state`）の行ロックでインクリメントするのをやめ、各テーブルの `updated_at` の最大値（MAX timestamp）を config 生成時に動的に取得してバージョン文字列とするか、Drizzle のトランザクション失敗時のリトライミドルウェアを明示的に組み込む。

### [重大度: medium] 表示スケジュール外の黒画面時におけるディスプレイ省電力未制御と mpv 強制終了漏れ
- 該当箇所: 要件定義書 14B節 / implementation-plan.md 6節（Assumption 1） / task_021 / acceptance-checks check_031
- 壊れ方: 表示スケジュール外で「画面を黒にする（動画も止める）」とあるが、ディスプレイの電源制御（DPMS / CEC）を行わず単に黒い画面（CSS の `background: black`）を表示するだけの設計になっている。大型ディスプレイはバックライトが点灯し続けたままとなり、省エネにならずディスプレイのバックライト寿命を著しく縮める。さらに、スケジュール外時刻に遷移した瞬間に mpv で動画が再生中だった場合、mpv プロセスを即座に強制終了（SIGTERM）させるロジックが計画されていないため、消灯時間帯にもかかわらず大音量で動画が再生され続ける。
- 根拠: Assumption 1 に「ディスプレイ電源の制御はしない」と明記されている（確信度: 高）。また task_021 に再生中動画の割り込み停止処理の記述がない。
- 修正案:
  1. HDMI CEC（`cec-client`）または KMS/DPMS（`wlr-randr --output HDMI-A-1 --off`）を用いて、表示時間外は物理的にディスプレイへの映像信号出力を OFF にする設計を追加する（映像信号が切れれば多くの商業ディスプレイは自動スタンバイに入る）。
  2. スケジュール判定ループで、表示時間外への突入時に mpv が稼働中であれば即座に SIGTERM を送信してプロセスをキルする処理を `player.py` に実装する。

### [重大度: medium] 動画再生時のオーディオデバイス排他・音量未制御・ハングアップ耐性の欠如
- 該当箇所: 要件定義書 18節 / TECH_STACK.md 10節 / task_003, task_021 / acceptance-checks check_007, check_034
- 壊れ方: mpv の起動オプションに音声関連の指定（`--volume` やオーディオドライバ）がない。深夜や共用ラウンジで、アップロードされた動画に過大音量の BGM が含まれていた場合に爆音で再生される。また、Pi の HDMI 音声ドライバ（ALSA / PipeWire）が一時的にビジー状態または未初期化の場合、mpv がオーディオデバイスのオープン待ちで永久ブロック（ハング）し、次の動画にも進めず、復帰もできず画面が停止する。
- 根拠: mpv はデフォルトでオーディオトラックの再生を試みるため、音声デバイスのエラーでハングまたは終了コード異常を起こすことがある（確信度: 高）。task_021 にプロセスのタイムアウト監視（Watchdog）が計画されていない。
- 修正案:
  - mpv の起動引数に固定音量設定（`--volume=50` など、管理画面で設定可能にするのが理想）と、動画の最長再生時間に合わせたハードタイムアウト（Python の `subprocess.run(..., timeout=duration + 5)`）を必ず設定する。音声不要な運用の場合は `--ao=null` オプションを用意する。

### [重大度: medium] Auth.js (NextAuth v5) の vinext (Cloudflare Workers) 上での非互換リスクとフォールバック未定
- 該当箇所: TECH_STACK.md 3.2節、20節 / implementation-plan.md 7節 / task_002, task_006 / acceptance-checks check_017, check_018
- 壊れ方: Cloudflare Workers 上で Next.js を動かす `vinext` 環境において、Auth.js (NextAuth) は Node.js 組み込み API（`crypto`, `stream`）への依存や Edge ランタイム特有の Cookie 処理の差異により、認証セッションの生成・復元で実行時例外を吐いてログイン不能になるリスクが極めて高い。計画書では task_002 でスパイクするとしているが、動かなかった場合の「自前セッション（署名付き Cookie）」へのフォールバック設計（具体的なテーブル設計、暗号化方式、CSRF 対策）が定義されておらず、Phase 1 のスケジュールが完全に崩壊する。
- 根拠: Next.js の Cloudflare Workers アダプター（OpenNext や vinext）において、Auth.js の互換性問題は頻出の既知トラブルである（確信度: 高）。
- 修正案:
  - Auth.js への過度な依存を最初から諦め、Workers の Web Crypto API（`crypto.subtle`）で完結する軽量な JWT セッション（`jose` ライブラリ等）と HTTP-Only / Secure Cookie を用いたシンプルな独自認証ミドルウェアを第一選択として計画を確定させる。

### [重大度: medium] Pi の時刻ズレに伴う天気情報（Stale判定）の誤動作と永久非表示化
- 該当箇所: 要件定義書 23節、39節 / task_005, task_013, task_014 / acceptance-checks check_016
- 壊れ方: 要件 23節に「天気は取得時刻が古い場合は天気欄を非表示にする」とある。Worker 側で定期取得した `weather.fetchedAt`（UNIX 秒）と、Pi の現在時刻を比較して stale 判定を行う設計にした場合、オフライン起動等で Pi の時刻が過去または未来にズレていると、差分計算が異常値（数十時間前、またはマイナス）になり、正常にキャッシュされている天気情報が即座に「古い」と判定され、画面から永久に非表示となる。
- 根拠: 「古い」の具体的な閾値（例: 3時間以上前など）が未定義であり、かつ時刻未保証のクライアント側で有効期限判定を行わせる設計の欠陥（確信度: 高）。
- 修正案:
  - stale 判定の責務を Pi のローカル時刻に依存させず、Worker 側で config 生成時に「この天気データは有効か」のブール値（`weather.isValid`）を付与して配信する。Pi 側では「最後の通信成功から X 時間以内」という起動後経過時間（monotonic clock）を基準にして表示可否を判断する。

### [重大度: medium] 大容量動画ダウンロード中の Heartbeat 停止による「OFFLINE」誤判定フラッピング
- 該当箇所: 要件定義書 25節 / TECH_STACK.md 18節 / task_020 / acceptance-checks check_012
- 壊れ方: 2GB などの大容量動画を Pi Agent がダウンロードしている最中、もし Python の同一スレッド/プロセス内で同期的なダウンロード処理が行われると、60秒ごとの Heartbeat 送信ループがブロックされる。結果として 5 分以上 Heartbeat が Cloudflare に届かず、大型ディスプレイで正常に稼働・ダウンロードしている最中にもかかわらず、管理画面上のステータスが勝手に「OFFLINE」に切り替わり、スタッフに「故障した」と誤認される。
- 根拠: task_020 では Python 標準ライブラリ中心で組むとあるが、ダウンローダーと Heartbeat 送信の並行性（threading または asyncio）の分離が明記されていない（確信度: 中）。
- 修正案:
  - Agent 内で Heartbeat 送信スレッド/タスクをダウンローダーから完全に独立させ、ダウンロード中であっても「現在動画 download 中（進捗 %）」のステータスを含めて確実に 60 秒ごとに Heartbeat を送信し続ける設計にする。
