### [重大度: critical] 端末トークン照合の404返却によるトークン列挙および完全オフライン運用不能
- 該当箇所: `implementation-plan.md` 6節 Assumption 5、9節「端末用API」、`task-list.json` task_011/task_012、`acceptance-checks.json` check_021
- 壊れ方: トークン照合失敗時に「存在を知らせないため404」を返すと、正しいエンドポイントパスに到達しているか否かがクライアント側から判別できない。さらに、URLパスパラメータ `/api/device/[token]/...` に生トークンを含めると、CDN/Workersログ、プロキシログ、リバースプロキシのアクセスログに認証情報が平文で残る。また、トークンを1回だけDLさせDBにはSHA-256しか持たない設計であるため、Piを新規交換・再キッティングする際に管理者がトークンを確認できず、全端末の再設定または孤立化が発生する。
- 根拠: 技術的事実（確信度: 高）。URLパスにクレデンシャルを含める方式はRFC 7230/OWASP API Security Top 10において情報漏洩のアンチパターン。また一般的なRESTにおいて認証不一致に404を返すとルーティングエラーと認証失敗が混同される。
- 修正案: 端末認証はパスパラメータではなく `Authorization: Bearer <deviceToken>` ヘッダーで行い、認証失敗時は標準の `401 Unauthorized` を返す。管理画面ではトークン紛失時に安全に再発行・再ダウンロードできる運用フローを明示する。

### [重大度: critical] Workers経由のR2動画中継とRangeリクエストによるWorker制限超過・コスト破綻
- 該当箇所: `implementation-plan.md` 6節 Assumption 6・7、9節「端末用API」、`task-list.json` task_008/task_012
- 壊れ方: 300MB〜2GBの動画ファイルをCloudflare Workersを経由して端末へプロキシ・Range中継すると、Workersのサブリクエスト制限、メモリ上限（標準128MB）、およびCPU時間制限（特に大容量ストリームの中継時）により切断またはクラッシュする。また、1ファイル2GBの動画を10MB単位のマルチパートでブラウザからWorker経由でアップロードすると、200回連続でWorkerを実行することになり、Workersリクエスト課金とWorker CPU時間を激しく浪費し、アップロード中にネットワーク断で頻繁に失敗する。
- 根拠: Cloudflare Workersの仕様（確信度: 高）。Workerランタイム経由でGB級のバイナリをストリーミング中継することは推奨されず、事前署名付きURL（Pre-signed URL）またはR2 Custom Domains（Token認証Workerで検証後、Cache-Tagやリダイレクトで直接配信）を使用するのが標準設計。
- 修正案: 「アクセスキーを持たせない方針」に固執せず、Workers側で認証を行った上で一時的なR2 Presigned Download/Upload URLを発行してR2と直接通信させるか、R2 BucketをWorkers認証付きカスタムドメイン配下に配置してパイプ処理をバイパスする。

### [重大度: critical] RTC未搭載Raspberry Piのオフライン再起動による時刻破綻とイベント全非表示
- 該当箇所: `要件定義書.md` 23節、45節（完成条件13）、`task-list.json` task_021、`acceptance-checks.json` check_013
- 壊れ方: Raspberry Pi 4にはハードウェアRTC（リアルタイムクロック）が搭載されていない。LANケーブルを抜いた（またはWi-Fi不通の）状態で再起動すると、システム時刻が過去（1970年または前回シャットダウン時など）に初期化される。この状態で起動したSignage Agentおよびブラウザは、現在時刻を1970年と認識するため、`lib/event-status.ts` の日付判定により今日のイベントが0件となり、NOW HAPPENINGやSTARTING SOONが永久に発火せず、サイネージが「イベントなし（キャッチコピーのみ）」または「表示時間外（黒画面）」のままフリーズする。
- 根拠: ハードウェアおよびLinuxの仕様（確信度: 高）。PiはNTPで時刻同期するため、オフライン再起動では正確な時刻を維持できない。fake-hwclockは前回のシャットダウン時刻を復元するだけであり、電源断から数時間〜数日経過していると時刻が大幅にずれる。
- 修正案: ハードウェア要件にI2C RTCモジュール（DS3231等、数百円）の追加を明記するか、Agentがオフライン起動時にローカルキャッシュ（`events.json` や `config.json` のタイムスタンプ）から「最後に同期した時刻」を起点に仮進めするフォールバック設計を入れ、時刻未確定時の表示モードを定義する。

### [重大度: critical] 端末同期の「content_version加算」による並行更新ロストとキャッシュ不整合
- 該当箇所: `implementation-plan.md` 9節、10節「Database Plan」、`task-list.json` task_007/task_009/task_010
- 壊れ方: お知らせ、イベント、デザイン設定、プレイリストがそれぞれ独立したServer Actionから「`app_state.content_version` を +1」する設計になっている。複数スタッフがほぼ同時にイベントとお知らせを更新した場合、`UPDATE app_state SET content_version = content_version + 1` の競合やロールバックにより、一方の加算が上書きされたり欠落したりする。さらに、各端末の `config_version` と全端末共通の `content_version` の合成ロジックが曖昧であり、合成本文のハッシュではなく単なるインクリメント値に頼っているため、バージョン番号が一致してしまい端末が304と誤認して更新を永久に取りこぼす。
- 根拠: 分散キャッシュ更新における技術的事実（確信度: 高）。単一シーケンスの手動インクリメントは並行トランザクションで競合に極めて弱く、Turso（libSQL）のような分散環境では書き込みトランザクションの競合エラーが頻発する。
- 修正案: 手動の `content_version + 1` を廃止し、端末向けconfigの出力JSON全体（または各コンポーネントのハッシュ）から計算した `ETag: W/"<SHA256>"` による完全なコンテンツハッシュ比較に変更する。

### [重大度: high] Wayland (labwc) 上でのChromiumとmpvの全画面奪い合いによるちらつき・背面に隠れる現象

### [重大度: medium] ChromiumキオスクとSignage AgentのIPC連携手段の未定義
- 該当箇所: `要件定義書.md` 20節、`task-list.json` task_021
- 壊れ方: 要件20節に「表示ページへの通知（動画再生前のフェードアウト指示、データ更新の通知）」とあるが、MVPではWebSocket不採用（要件21節）としている。Agent（Python）からChromium（ローカルWebページ）へ動画再生直前の「500ms暗転」を指示する手段として、計画書では「`/local/state` を1秒ごとにポーリングする」と記載されている。1秒間隔のポーリングでは、最大1000msの遅延が発生するため、「暗転指示から500msで動画起動」というタイミング制御が完全に破綻し、暗転前に動画が立ち上がる、または暗転したまま動画が始まらない不整合が頻発する。
- 根拠: リアルタイム制御の技術的事実（確信度: 高）。1秒のHTTPポーリングでミリ秒単位のフェードアウト同期を行うことは不可能。
- 修正案: ローカルAgentとChromium間の通信にServer-Sent Events (SSE) またはローカル専用の軽量WebSocket（Pythonの組み込みまたはUnixドメインソケット経由）を採用し、イベント駆動で遅滞なくフェード指示を伝達する。

### [重大度: medium] 定期動画再生時の「終了後復帰」における音声残留とゾンビプロセス
- 該当箇所: `要件定義書.md` 18節、`task-list.json` task_021、`acceptance-checks.json` check_034
- 壊れ方: mpvをPythonの `subprocess` 等で起動・監視する設計になっているが、動画ファイルが壊れている、コーデックが非対応、あるいはオーディオデバイスがビジー状態の場合、mpvがハングアップして終了シグナルを返さないことがある。この時、Python側がタイムアウト処理を持たないとサイネージ全体が停止する。また、Chromium側で動画や音声を含むお知らせを流すような拡張があった場合、mpvの音声とブラウザの音声が競合してALSA/PulseAudio/PipeWireがクラッシュする。
- 根拠: Linuxメディア再生の実装上の落とし穴（確信度: 高）。CLIメディアプレイヤーのサブプロセス管理には厳密なタイムアウト、強制終了（SIGKILL）、IPC終了監視が必須。
- 修正案: `player.py` に動画のメタデータから取得した `duration + 5秒` の強制キルタイムアウトを実装し、mpv IPCソケット（`--input-ipc-server`）を利用して再生状態を直接監視・制御する。

### [重大度: medium] 受入チェック check_003（30秒以内反映）の測定方法の非現実性
- 該当箇所: `acceptance-checks.json` check_003
- 壊れ方: 「登録後30秒以内にサイネージへ反映」の検証方法として「ストップウォッチと Pi の表示を動画撮影」と記載されている。しかし、ポーリング間隔が「30秒」であるため、スタッフが保存ボタンを押した瞬間がポーリング直後だった場合、次のポーリングまで最大30秒かかり、さらにネットワーク遅延＋JSONパース＋DOM描画が加わるため、物理的に「30秒以内」を確実に達成することは不可能（理論上30〜35秒程度になる）。テストが確実にfailする。
- 根拠: 数学的・論理的必然（確信度: 高）。ポーリング周期30秒のシステムにおいて、最悪ケースのレイテンシは「30秒 + 処理時間」となり、30秒を下回る保証はできない。
- 修正案: 要件の反映時間を「45秒以内」に緩和するか、ポーリング間隔を「15秒〜20秒」に短縮して30秒要件を満たせるように設計を変更する。
